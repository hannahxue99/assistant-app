# 产品需求与代码更新流程

后续每项产品需求统一按照以下阶段推进。

## 1. 需求分析

- 检查现有产品文档、设计稿、数据结构和代码实现。
- 明确目标、影响范围、异常场景及验收标准。

## 2. 设计与方案先行

- 先更新设计稿或交互说明。
- 只要需求涉及页面、视觉、交互或导航，必须同时提供可查看的具体图示，不能只交付文字描述：
  - 页面布局变化：提供线框图或页面设计图。
  - 样式调整：提供修改前后对比图。
  - 点击、编辑、确认等交互：提供关键状态图。
  - 页面跳转或业务流程变化：提供流程图。
- 同步给出技术解决方案，包括数据结构、页面交互、迁移策略、风险和测试方案。
- 用户确认设计和方案后，才进入编码阶段。

## 3. PR 实现

- 从稳定基线创建独立 Git 分支。
- 在分支中完成代码、数据迁移、测试和相关文档更新。
- 创建 PR，清晰列出改动、验证结果、兼容性与回滚方式。
- 不直接覆盖历史版本，不使用破坏性命令清除已有改动。

## 4. 验收与合并

- 先完成自动化检查，再提供手机端手工验收步骤。
- 用户验收通过后合并 PR。
- 保留提交和 PR 历史，出现问题时可定位并回滚到上一版本。

## 5. 经验与知识沉淀

验收完成后、需求关闭前，将本次经验写入 `docs/knowledge/`，并更新知识索引。至少记录：

- 需求背景和最终产品决策，以及未采用方案的关键原因。
- 问题根因或实现中的核心技术取舍。
- 踩坑、错误现象、排查路径和最终解决办法。
- 可复用的数据结构、交互模式或代码方案。
- 自动化测试与手机端验收方法。
- 关联 PR、关键提交和明确的回滚点。

简单改动可追加到已有专题；形成独立经验时新建专题文档。知识不能只留在聊天记录、个人记忆或 PR 评论中。

## 当前状态

自 2026-09-03 起，项目已启用 Git 版本管理，并连接 GitHub 私有仓库
`hannahxue99/assistant-app`。`main` 作为稳定基线；后续产品改动从独立分支开发，
通过 PR 评审和验收后再合并，并在关闭需求前完成经验沉淀。
