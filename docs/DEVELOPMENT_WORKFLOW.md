# 产品需求与代码更新流程

后续每项产品需求统一按照以下阶段推进。

## 1. 需求分析

- 检查现有产品文档、设计稿、数据结构和代码实现。
- 明确目标、影响范围、异常场景及验收标准。

## 2. 设计与方案先行

- 先更新设计稿或交互说明。
- 只要需求涉及页面、视觉、交互或导航，必须同时提供可查看的具体图示，不能只交付文字描述：
  - 页面布局变化：提供线框图或页面设计图。
  - 样式调整：提供修改前后对比图。
  - 点击、编辑、确认等交互：提供关键状态图。
  - 页面跳转或业务流程变化：提供流程图。
- 同步给出技术解决方案，包括数据结构、页面交互、迁移策略、风险和测试方案。
- 用户确认设计和方案后，才进入编码阶段。

## 3. PR 实现

- 从稳定基线创建独立 Git 分支。
- 如果需求已在其他窗口或任务中创建 PR，先检查 PR 描述、提交、评论、检查结果、设计文档和分支基线；可继续使用时直接接管原分支和 PR，不重复开发。
- 在分支中完成代码、数据迁移、测试和相关文档更新。
- 创建 PR，清晰列出改动、验证结果、兼容性与回滚方式。
- 不直接覆盖历史版本，不使用破坏性命令清除已有改动。

## 4. 验收与合并

- 先完成自动化检查，再提供手机端手工验收步骤。
- 自动化通过只代表“可进入真机验收”，不等于上线完成。
- 按改动类型选择真机更新方式：
  - JS、文案、样式：Metro Reload。
  - 原生依赖、权限、图标、签名或原生配置：重新编译并覆盖安装。
  - Bundle ID 变化：视为新 App，必须先设计并验证数据迁移。
- Debug 测试 App 也属于产品验收界面，不得在用户导航中暴露组件预览、调试工具、测试数据或开发文案。
- 用户验收通过后合并 PR。
- 保留提交和 PR 历史，出现问题时可定位并回滚到上一版本。

## 5. 经验与知识沉淀

验收完成后、需求关闭前，将本次经验写入 `docs/knowledge/`，并更新知识索引。至少记录：

- 需求背景和最终产品决策，以及未采用方案的关键原因。
- 问题根因或实现中的核心技术取舍。
- 踩坑、错误现象、排查路径和最终解决办法。
- 可复用的数据结构、交互模式或代码方案。
- 自动化测试与手机端验收方法。
- 关联 PR、关键提交和明确的回滚点。

简单改动可追加到已有专题；形成独立经验时新建专题文档。知识不能只留在聊天记录、个人记忆或 PR 评论中。

## 6. 上线定义与信息回收

“上线”必须区分两个状态：

- 代码上线：PR 已合并到 `main`。
- 设备上线：手机已通过 Reload、Debug 覆盖安装、Release 安装或正式分发运行对应版本。

合并前回收并记录：

- 需求范围、最终决策和明确的非目标。
- PR 地址、分支、合并提交和回滚点。
- 类型检查、自动化测试、iOS 构建或导出结果。
- 验收设备、系统版本、Debug/Release 类型和真机用例。
- 是否涉及原生依赖、Bundle ID、数据库迁移、数据备份或兼容风险。
- 验收中发现的问题、处理结果和未解决风险。
- 已更新的设计、测试、知识库和基础规则。

统一使用 [`docs/RELEASE_CHECKLIST.md`](RELEASE_CHECKLIST.md) 作为上线记录模板，避免只在聊天中口头汇报。

收口顺序固定为：

```text
用户验收通过
→ 回收上线信息
→ 更新知识库与基础规则
→ 合并 PR
→ 同步本地 main
→ 按需交付 Debug/Release 手机版本
→ 输出最终上线记录
```

## 当前状态

自 2026-09-03 起，项目已启用 Git 版本管理，并连接 GitHub 私有仓库
`hannahxue99/assistant-app`。`main` 作为稳定基线；后续产品改动从独立分支开发，
通过 PR 评审和验收后再合并，并在关闭需求前完成经验沉淀。
