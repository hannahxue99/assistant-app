# 秘书 + 导师：产品决策账本

> 版本说明（2026-09-17）：本文讨论阶段使用的“V0.3”已正式升级命名为 **V1 完整愿景**。文件保留原始决策编号；产品总纲和当前实现状态以 [`PRD.md`](../../PRD.md) 为准。

状态：讨论中。本文只记录已经确认、当前采用和仍待讨论的决策；最终确认前不进入生产代码。

## 一、已经明确

1. 产品愿景：知道用户最近在做什么，能够长期陪伴、理解用户，并在合适的时候给予引导。
2. PMF 表述：一个长期懂你的私人 AI：像秘书一样帮你料理当下，像导师一样帮你看清方向。
3. 产品必须提供简单、方便的交互，让用户自然地与秘书 / 导师互动。
4. 方案采用逐步收敛：已经明确的部分不重复打开，模糊部分逐项讨论。
5. 讨论过程必须保持可视化，但不再为每个问题重新生成完整线框稿。日常维护“一张中文交互总图”，每轮只增量调整相关节点；在最终方案里程碑再生成高保真线框稿。
6. 用户输入入口统一，输出交互也尽量统一；产品不因为“记录 / 事务 / 困惑”切换成三套明显不同的操作方式。
7. 统一对话中的用户消息、助手回复和办理回执需要被保存；对话记录本身就是用户可回看的事件历史，不再重复建设独立的“经历 / 记录”内容流。
8. 助手页采用“用户看到连续对话，系统在后台自动分段”的方案；用户不需要手动创建和管理新会话。
9. 后台会话摘要只服务 AI 上下文，暂不在界面中展示，也不用于生成用户可见的会话标题或预览。
10. 长期记忆采用分级准入：用户明确表达或多次出现的非敏感证据可以生效；单次推断先等待确认；敏感内容默认不保存或必须明确确认。所有长期记忆均可追溯、纠正、替代和删除。
11. V1 教练提醒只在首页展示，不主动推送；最多 5 条，来源受限，每条说明触发原因，点击后进入助手并携带上下文继续处理。
12. 教练提醒只有两种首页操作：点击提醒进入助手处理，或选择“不再提醒”；不提供“稍后”。“不再提醒”表示该条提醒永久不再出现。进入助手后直接围绕事项推进，再根据处理结果更新相关状态。
13. 教练提醒的内容不得与本周待办重复。待办回答“要做什么”，提醒必须提供待办之外的增量价值，例如遗漏、冲突、停滞、机会、关联或反复模式；待办可以作为判断信号，但不能被原样复述成提醒。
14. 用户对提醒产生相关回应或操作后，原提醒才退出首页；后续是否产生新提醒，取决于问题状态是否发生有意义的变化，而不是按时间重复催促。
15. AI 教练按“每天复盘一次”的逻辑粒度运行，复盘不绑定首页打开事件；生成的提醒仍只在首页展示，不主动推送。
16. 每日复盘采用“系统后台尽力执行 + App 任意页面进入时检查并补跑”的策略。App 长期未打开或被系统终止时不保证每天运行；不为保证准点复盘而在 V1 引入云端调度。
17. 教练提醒允许两条触发链路：用户的新输入或行为触发，以及 AI 对已有事件、记忆和状态的主动复盘触发。无论来源，都必须通过证据、增量价值和去重门槛。
18. 所有消息都保存到助手对话，但只有值得持续跟踪的内容才创建或更新首页“事件”。事件关系分为新事件、已有事件延续、相似但独立并建立关联；一次性闲聊或普通信息不强制归入事件。
19. 不提供“长期待办”模块或“全部待办”页面，用户无需直接浏览长期事项；底层数据继续保留，进入本周时自动投影到首页本周待办，用户可通过助手查询、修改或取消。
20. 没有明确日期的行动意图先作为隐藏待办保存，助手随后可以在当前对话中轻量追问时间；追问不阻塞保存，补充日期后才进入首页。它不会仅因长期未安排而被原样生成成教练提醒。
21. 一次性行动默认不创建事件；如果后续出现多次更新、多步骤目标或持续关注，系统可再建立事件并回溯关联早期消息和隐藏待办。系统自动创建或更新事件时，在助手回复下方显示轻量归属提示并允许更改。
22. “我的”只展示长期记忆，不展示短期记忆；短期信息只在后台帮助 AI 理解当前状态。
23. 产品不再把“短期记忆”定义为独立内容库，统一改称后台“当前状态快照”。它由近期消息、进行中事件、未完成待办和相关长期记忆生成，可以缓存，但删除缓存后必须能够重建。
24. 首页事件列表 V1 暂时展示全部事件，不按活跃度自动移出首页；置顶事件优先，其余按最近更新时间排序。
25. 事件采用“过程追加、当前状态更新”的双层结构：历史动态只追加并可追溯，事件标题、当前状态摘要和更新时间可随新进展更新；首页展示当前状态，事件详情保留发展过程。
26. 所有与事件相关的消息都保留后台关联，但事件动态只追加有意义的状态变化，包括重要新信息、决定、阶段结论、目标或阻碍变化、关联待办变化以及纠正；普通追问、重复表达、寒暄和重复总结不进入事件动态。
27. 同一条来源消息可以同时形成事件信息和长期记忆，但两者必须职责不同并相互关联：事件记录事情的过程和当前进展，长期记忆记录跨越具体事件仍然成立的用户认知；不在两处复制同一句内容。
28. 长期记忆只保存“关于用户、跨事件仍然成立、会影响未来协助方式”的认知，不作为通用长期档案。具体项目结论、待办、临时状态、完整对话和未经确认的单次推断不进入长期记忆。
29. “我的”中的长期记忆不展示形成依据和来源，也不提供“查看来源”入口；依据、来源和准入方式只在后台保留，供冲突判断、纠错和必要时在助手对话中解释。
30. “我的”只展示已经生效的长期记忆。尚未达到准入条件的候选记忆不进入“我的”，仅在合适的助手对话节点请求用户确认。
31. 用户明确要求记住，或信息明确、稳定、非敏感且已有重复证据时，长期记忆可以自动生效，并在助手消息内给出可撤销的轻量回执；单次推断和敏感信息必须先得到用户确认。
32. 助手应自主完成低风险、可逆的理解和整理，不把分类、关联、摘要等内部判断反复交给主人决定；只有涉及敏感信息、明显歧义、高影响或不可逆后果时才请求用户选择。
33. 助手默认执行了会改变用户数据或后续行为的操作时，必须在当前回复中给出轻量回执，例如创建或修改待办、创建或更新事件、保存长期记忆以及改变提醒状态；纯内部的消息落库、分段、摘要、检索和缓存不单独提示。
34. 同一轮回复产生的所有用户可感知操作合并为一个“已处理”回执；回执逐项列出操作，并仅提供必要的撤销或更改入口，不为每个操作单独发送系统消息。
35. 待办以用户表达或接受的行动意图为准，不要求固定命令；AI 自己提出的建议不能直接成为用户待办，只有用户接受或表达准备执行后才创建，并通过“已处理”回执告知。
36. 无日期待办采用“先保存、当场最多追问一次”的策略；用户未回答或明确暂不安排时继续隐藏且不阻塞对话，只有未来再次出现相关上下文时才可以自然询问，不按时间重复追问或原样生成教练提醒。
37. 对话消息、事件、待办和长期记忆平时独立保存；删除存在衍生关系的来源消息时，系统必须显示受影响内容，并让用户选择仅删除消息或同时删除由它形成的相关内容。一项认知仍有其他有效来源时，删除单个来源后重新判断，不机械级联删除。
38. 后台会话分段以明显语义切换为主要边界，以单段容量上限为强制兜底，时间间隔只作辅助信号。新对话上下文保留最近 4–6 轮原话、当前段摘要和少量相关历史分段，并按事件、待办和记忆检索旧内容；分段与摘要不对用户展示或询问。
39. 后台当前状态快照随消息、事件、待办和长期记忆的变化做增量更新，并在每日复盘时完整校准；能由结构化变化计算的内容本地更新，语义变化与主对话或会话摘要共用模型结果，不为每条消息单独增加一次模型调用。重建失败时暂用旧快照并直接补入最新结构化数据。
40. V1 采用“完整的最小闭环”作为范围：三个 Tab、连续对话及保存、待办 / 事件 / 长期记忆沉淀、后台上下文与当前状态快照、首页每日教练提醒，以及从提醒返回助手继续处理必须共同成立。首页教练提醒属于 V1 必需能力，不能仅因主要基础功能已经上线就移出 V1。
41. V1 不包含云端定时调度、主动推送、外部系统代办、用户手动管理会话、秘书 / 导师模式切换、复杂记忆图谱和事件自动归档。现有待办、聚合主题和用户原声必须保留并迁移。
42. 对话消息、事件、待办和长期记忆是四类独立保存、通过关系连接的一等对象，不互相作为附属记录：消息保存完整表达和历史证据；事件保存持续事情的当前状态与关键进展；待办保存用户承诺执行的行动、日期和完成状态；长期记忆保存跨事件仍成立并影响未来协助方式的用户认知。同一条消息可以关联或派生多个对象，但对象一经形成便有独立生命周期，删除时遵守第 37 条的影响告知和非机械级联规则。
43. 单轮处理采用“一次 AI 理解 + 本地校验 + 事务保存 + 成功回执”：用户原始消息先落库；AI 一次返回自然回复和拟执行操作；系统校验权限、歧义和数据约束后，一次性保存助手回复、有效对象及关系；只有实际保存成功才生成“已处理”回执。每次请求使用唯一编号保证重试幂等；模型或网络失败时保留用户消息并允许重试，保存失败时不得向用户宣称已经完成。
44. 首页不新增助手对话框或快捷输入框；用户从底部中间的 AI Tab 进入完整对话页。该 Tab 使用智能机器人图标，并以助手昵称作为用户可见标签，不显示生硬的功能名“助手”。当前工作昵称暂用“小知”，图标暂用“灵动机器人”（未选中为轮廓脸、选中为实心脸）；两者均保留后续品牌阶段调整的空间。
45. 用户点击首页提醒后进入“小知”，小知以一条普通、可保存的助手消息主动接话，内容包含必要背景和一个推进问题，不建设特殊处理页。接话内容随提醒生成而预先准备，点击时不新增模型调用；同一提醒只落一条接话消息，重复进入定位到原消息。仅打开或读到接话不算处理；用户无相关回应便离开时，提醒回到首页并显示“继续处理”，产生相关回应或操作后原提醒才退出。
46. 用户普通点击“小知”Tab 时安静回到连续对话，不因页面打开生成问候、弹出键盘或调用模型；只有从提醒或具体事项携带上下文进入时，小知才主动接话。首次无对话时只显示本地静态引导和少量自然语言示例，不写入消息历史，也不划分使用模式。
47. 现有聚合主题详情升级为事件详情：顶部显示事件名、更新时间、置顶与更多操作；主体依次显示可更新的当前状态、该事件下已经安排时间的待办、只追加有意义变化的关键进展；隐藏待办不在此暴露。页面不设置独立输入框，底部使用“和小知聊这件事”进入同一条连续对话并携带事件上下文。旧聚合主题及其原始条目完整保留为事件历史来源，不因升级丢失。
48. “我的”不再保留与长期记忆并列的独立画像卡。升级时按语义拆分原画像：稳定偏好、原则、长期目标和反复模式进入长期记忆；有时限的近期目标进入当前状态，已经形成持续主线的可进入事件；过期或含义不清的内容保留原始值，并在后续合适对话中轻量确认。迁移完成后由小知给出一次合并回执，所有原始值保留为迁移来源与回滚依据；通知、日历、理解引擎和数据管理设置继续保留在“我的”。
49. “我的”以长期记忆为主内容，设置与数据位于下方，不把记忆藏进二级页，也不生成难以逐项修正的整篇画像。已生效记忆以原子卡片连续展示，每张只显示类别、简短认知以及“修改 / 忘记”入口，不展示依据、来源或置信度；不设置手动新增按钮，用户通过与小知对话表达“记住”。无记忆时只显示静态空态，不为填充页面生成推断。
50. 统一搜索入口放在“小知”页右上角，首页和“我的”不再分别设置搜索框。精确搜索在本地执行，不调用模型，覆盖完整对话消息（包括迁移后的原声）、事件、待办和已生效长期记忆；需要理解、归纳或追问的自然语言回忆仍通过与小知对话完成。
51. 统一搜索的“全部”结果采用关系感知归组：确有关系的事件、待办和对话合并为一个事件组，事件作为组入口，子项可直达具体待办或原对话；跨事件仍成立的长期记忆继续独立展示。没有关系的同词命中保持为独立结果，不能仅凭关键词强行合并。顶部提供“全部 / 事件 / 对话 / 待办 / 记忆”筛选；同一来源产生的多个对象在“全部”中去重，但各类型筛选仍可查看完整命中。隐藏待办允许通过用户主动搜索找到，但不因此新增可浏览的长期待办页面。

## 二、当前采用，但尚未最终确认

1. 秘书和导师是同一个助手的两种行为，不设计成两个机器人或两个模式。
2. 用户通过一个自然语言入口表达，不要求预先选择“记录 / 事务 / 困惑”。
3. 现有 App 渐进演化，不整体推倒重构。
4. 顶层功能区域为“首页 / 助手 / 我的”，其中用户可见底部标签为“首页 / 助手昵称 / 我的”。中间昵称 Tab 是独立对话页并保存完整对话；“我的”包含专门的记忆区。
5. 对话与记忆分层：完整消息历史归“助手”；从消息中提炼且通过准入规则的长期认知归“我的 → 记忆”；近期状态只进入后台当前状态快照。
6. 首页暂分两层：第一层“本周”，包含功能保持不变的本周待办，以及不超过 5 条的教练提醒；第二层“事件列表”，承接现有聚合主题能力。
7. 所有输入暂定进入同一个助手会话容器，助手使用同一种消息形态回应；办理结果、话题归属和记忆提示作为消息内的轻量附加信息出现。
8. 信息暂按三层组织：对话消息保留发生过什么，话题连接同一主线及相关主线，长期记忆保存当前仍有效的理解。底层仍可保留事件模型供任务和审计使用，但不单独形成一个用户页面。
9. 现有用户原声迁移进可搜索的助手消息历史，不再建设重复的“经历 / 记录”页面；旧原文、待办和聚合关系不删除。
10. 会话摘要暂定为后台可重建缓存：它覆盖某一段消息，用于历史检索和后续对话上下文；完整原始消息始终保留，摘要不直接等同于短期或长期记忆。
11. “我的 → 记忆”只承载可见、可纠正的长期认知，包括稳定偏好、重要关系、长期目标、原则和反复模式。短期状态不在界面中展示，只在后台参与上下文组织；所有长期记忆必须能追溯到来源消息，但不会复制完整对话。
12. 记忆界面暂采用原子卡片作为推荐默认值：一张卡只表达一项认知，用户侧保持为简短内容及修改、忘记操作；依据、来源和关系图谱只在后台存在，不直接暴露给用户。

## 三、仍待讨论

1. 后台会话分段的具体 Token 阈值、摘要字段和检索数量，需要在实施方案中结合所用模型验证。
2. 后台当前状态快照的缓存字段、版本号和失败重试间隔，需要在实施方案中确定。

## 四、低 Token 讨论格式

每轮只处理一个高影响决策，使用以下格式：

- 当前问题
- 2–3 个方案及代价
- 推荐默认值
- 一个待用户回答的问题

用户确认后，只把结论和对应节点增量更新到本文及同一张交互总图，不重复生成整套说明或多个版本图稿。

交互总图使用中文节点和箭头表达：用户输入 → 意图分流 → 系统回应 → 页面变化 → 数据沉淀。未确认节点标“待定”，确认后改为“已定”。只有布局、视觉层级需要评审时才制作手机线框稿。

## 五、完成条件

以下内容全部确认后，才生成一次最终设计稿与实施方案：
