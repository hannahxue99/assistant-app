# 首页减法、旧日志导入与小知输入框设计

状态：设计已确认，代码已实现，等待 Dev 端验收

视觉稿：[首页、旧日志迁移与 Codex 式输入框](../../design/home-legacy-import-codex-composer-v16.svg)

## 1. 产品范围

本轮包含三个相互配套的变化：

1. 首页彻底移除“主人的备忘录”模块，包括聚合消息、用户原声、模块搜索以及首页底部快速记录框。首页只保留“本周待办｜全部待办”和事件列表，唯一输入入口仍是“小知”。
2. “我的 → 数据管理 → 导入数据”自动识别老版本 Markdown 导出日志。旧原文按原时间进入小知连续对话；待办直接恢复；旧主题恢复为事件。
3. 小知底部输入框参考 Codex 的克制形态与语音转写习惯：一个圆角输入容器承载键盘、语音回显、编辑和发送，不增加当前没有业务能力的附件按钮。

## 2. 旧版日志导入

### 2.1 选择方案

采用确定性解析，不调用大模型。老版本导出的格式固定为：记录类型与创建时间位于二级标题，原文位于引用块，可选字段包括理解、主题、标签和时间。解析器严格识别这一格式，先形成预览，再由用户确认写入。

备选方案 A 是把整份日志交给模型重建，优点是容错高，缺点是可能改写原文、误判日期和产生 Token 成本，不采用。备选方案 B 是只恢复为对话文本，最简单但会丢失待办和事件，不采用。

### 2.2 映射规则

- 每条旧记录都生成一条 `user` 消息，内容为原文，`createdAt` 使用旧标题时间，来源标记为 `legacy`。它按时间插入连续历史，不生成虚假的助手回复。
- `待办` 保留原文、理解标题、到期时间和完成状态，直接写入待办事实表。旧文件没有日期时仍导入，但作为隐藏待办，不强行猜日期。
- 同一 `主题` 形成一个事件。主题名是事件标题；最新一条理解结果作为当前状态；主题下每条记录按原时间成为一条事件进展，并与对应小知消息建立来源关系。
- `想法 / 信息` 没有主题时只进入小知历史；有主题时同时进入相应事件。
- 导入不触发小知回复、不重新理解内容、不创建操作回执，也不消耗模型 Token。

### 2.3 去重与事务

老文件没有稳定 ID，因此使用“规范化原文 + 类型 + 创建时间 + 到期时间 + 主题”的稳定指纹生成导入 ID；同一文件重复导入不会重复创建。导入前同时用指纹检查本地旧条目，避免用户在原设备上导入自己已有的数据。

整份文件先完成结构与时间校验，再在 SQLite 事务内写入条目、消息、待办、事件、进展和关系。任一环节失败则整体回滚。提醒同步在主事务提交后执行，失败进入现有补偿队列。

### 2.4 预览与反馈

现有导入弹层增加格式类型：`新版完整备份` 或 `旧版导出日志`。旧日志预览展示“对话多少条、待办多少条、事件多少个、重复多少条”。成功反馈也按这四项说明。损坏、手写或不符合旧格式的 Markdown 不做模糊猜测，提示具体失败记录，现有数据不变化。

## 3. 小知输入框

### 3.1 视觉结构

输入区使用单个白色圆角容器，边框和阴影保持克制；一行时紧凑，多行向上增长，最多五行后内部滚动。麦克风位于左下，发送按钮位于右下，文字区占据中间。发送按钮只有存在有效文字且未处理中时使用品牌橙色，其余为弱灰。

### 3.2 语音交互

采用“点击开始、点击停止”，替换当前“按住说话”。转写的临时结果实时回显到同一个文本框，并保留用户开始语音前已经输入的文字。停止后文字留在输入框，可修改后再发送；不会因为停止录音自动提交。该选择借鉴 Codex / ChatGPT Dictation 的核心原则：语音先成为可检查的文字，再作为用户消息发送。

备选方案是保留按住说话，优点是实现简单，但长表达容易误松手且不符合用户指定的参考方向；另一备选是独立实时语音会话，交互更重并改变模型调用与成本，本轮不做。

### 3.3 四种状态

- 空闲：显示“发消息给小知”，麦克风可用，发送按钮置灰。
- 输入：文字区向上增长，发送按钮点亮；语音和键盘内容可以接续。
- 正在听：边框与麦克风使用品牌色，左下按钮变为停止；临时转写实时回显；发送暂不可用。
- 小知处理中：沿用已确认规则，输入框先清空并整体置灰，不显示第二个加载转圈；上方回复完成后恢复。

语音权限拒绝、识别失败和发送失败继续在输入框下方就地提示。发送失败时恢复原文字；语音失败时保留已经转写的部分。切换 Tab 或组件卸载时终止识别，不自动发送。

## 4. 页面与数据流

### 首页

移除备忘录相关的查询、筛选、搜索、原声卡片和快速输入代码，而不是仅把 UI 隐藏。旧 `entries` 表暂不删除，继续作为待办、导入兼容与回滚来源。

### 导入

`选择文件 → 自动识别 V2 / 旧日志 → 无写入预览 → 用户确认 → 单事务映射 → 刷新小知 / 待办 / 事件 → 提醒补偿`

新版 V2 数据胶囊的现有恢复行为保持不变，但导入完成后也立即执行消息与事件投影，不再要求重启 App 才能看到。

### 输入

`点击麦克风 → 权限检查 → 流式系统转写 → 同一 TextInput 回显 → 点击停止 → 编辑 → 发送 → 本地先保存 → 小知处理`

本轮继续使用已安装的系统语音识别模块，不新增原生依赖，因此 Dev 版只需 Metro Reload。

## 5. 边界情况

- 老日志记录顺序混乱：最终按解析出的 `createdAt + 稳定 ID` 排序。
- 两条内容相同但时间不同：视为不同记录；内容与时间都相同则去重。
- 旧待办已完成：保留完成态，不出现在未完成列表。
- 旧待办时间无法解析：整份文件在预览阶段拒绝，指出具体记录，不把错误日期写入数据库。
- 同名主题：合并进同一个旧事件；已有同源旧事件时追加缺少的进展，不重复建事件。
- 导入记录早于或晚于现有对话：都按原时间进入正确位置，不强行追加到最末端。
- 语音过程中已有键盘文字：语音转写追加在原文字后；停止后可任意编辑。
- 处理中、初始加载失败或未配置模型：输入框状态继续沿用现有约束。
- 动态字体与长文本：输入框自然增高到五行；按钮维持至少 44×44 点击区。

## 6. 验收标准

1. 首页不再显示“主人的备忘录”、聚合消息、用户原声、搜索和底部记录框，只保留待办与事件。
2. 选择基线版本导出的 Markdown，预览能正确给出对话、待办、事件和重复数量；确认前数据库没有变化。
3. 导入后每条旧原文按原时间出现在小知历史；没有自动生成的 AI 回复。
4. 旧待办的标题、日期、完成态正确；本周和全部待办仍按既定 7 天窗口显示且互不重复。
5. 旧主题生成或合并为事件，当前状态取最新记录，详情按时间保留进展与来源关系。
6. 同一旧文件重复导入不会重复创建；任一结构错误时全部不写入。
7. 小知输入框一至五行自然增长；键盘文字、语音转写和发送都在同一个容器内完成。
8. 点击麦克风开始，实时回显文字；再次点击停止，文字可编辑且不会自动发送。
9. 小知处理中输入框清空置灰且不显示内部转圈；失败时原文正确回填。
10. TypeScript、旧格式解析、事务回滚、幂等、消息投影、事件映射和输入状态测试均进入 `npm test`；`npm run ci` 通过后在当前 Dev App Reload 验收。

## 7. 一个已发现但不在本轮扩大的问题

当前 V2 导出格式早于小知一等消息与事件表，只能完整保存旧 `entries / profile / topicPreferences`，不能完整备份后来生成的小知回复、操作回执和新事件。本轮先保证“老版本文件能安全进入新结构”，不把导入兼容与 V3 全量备份混成一次高风险改造；V3 应作为紧接着的独立数据安全任务完成。
