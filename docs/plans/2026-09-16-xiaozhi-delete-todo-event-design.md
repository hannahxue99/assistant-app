# 小知删除待办与事件设计

## 目标与范围

让用户通过小知的键盘或语音输入删除已有待办和事件，并保持候选匹配、日历同步、事务一致性、操作回执和整轮撤销。原始对话消息不随对象删除。

视觉与状态流：[小知删除待办与事件](../../design/xiaozhi-delete-todo-event-v21.svg)

本轮只新增小知语义删除，不给首页或事件详情增加删除按钮，不支持删除对话消息。

## 产品规则

### 删除待办

- 用户必须明确表达删除、取消或不再保留某条待办；模型不能从“可能不做”“先放放”推断删除。
- 唯一匹配后直接删除，不追加确认；多个候选无法唯一确定时只追问一个问题，操作数组为空。
- 首页和事件详情引用的是同一条待办实体。删除该实体后，它会同时从首页列表和所有关联事件中消失，不存在两份数据分别删除。
- 有苹果日历映射时，沿用现有 `calendar_delete` 补偿队列删除对应日程；日历临时失败不回滚本地删除，后续同步重试。
- 回执显示“删除待办：{标题}”，支持整轮撤销。撤销恢复待办、原有关联关系及日历同步。

### 删除事件

- 唯一匹配事件且没有关联待办时，直接删除。
- 存在关联待办、用户没有说明去留时，小知必须先问：“这个事件还有 N 条关联待办，要一起删除吗？”本轮不产生删除候选。
- 用户回答“保留待办”后，只删除事件；待办仍留在首页，不再通过该事件展示。
- 用户回答“一起删除”后，在同一个事务内删除事件及它的全部关联待办，包括未完成和已完成待办。
- 用户第一次就明确“事件和关联待办一起删”或“事件删掉、待办保留”时直接执行，不重复提问。
- 用户未回答确认问题便离开时，事件和待办保持原状；之后继续该话题仍可回答去留。

## 交互与语音

语音输入仍只负责系统转写，转写文字进入与键盘完全相同的小知请求。删除能力不依赖输入方式，不新增语音专用规则。

示例：

- “删除明天交报告的待办” → 唯一匹配后直接删除。
- “贷款这件事不要了，删除事件” → 若有两条关联待办，先询问是否一起删除。
- “贷款事件和里面的待办都删了” → 直接删除事件与全部关联待办。
- “删掉那个还款” → 有多个候选时追问具体哪一条，不做任何删除。

## 模型协议

新增两个候选操作：

```json
{"key":"...","type":"delete_todo","todo_id":"候选ID"}
```

```json
{
  "key":"...",
  "type":"delete_event",
  "event_id":"候选ID",
  "linked_todo_policy":"keep|delete"
}
```

- `delete_todo` 只能引用本轮 action context 中的待办候选。
- `delete_event` 只能引用事件候选。事件存在关联待办时必须给 `linked_todo_policy`；用户未说明时模型不得猜测，必须回复追问且不输出操作。
- 事件 action context 增加关联待办总数、未完成数和有限明细，避免模型根据截断列表报错数量。
- 删除操作进入现有 decision log，保存模型候选、校验结果、最终提交或拒绝原因。

## 本地提交与存储

### 待办

待办继续使用 `entries(kind='task')`。提交 `delete_todo` 时：

1. 用候选快照的 `revision_at` 做乐观锁校验。
2. 保存待办完整快照以及所有有效 `belongs_to` / source 关系。
3. 将关系标记为 undone，删除 `entries` 和 FTS 行；SQLite 日历触发器写入删除补偿任务。
4. 写入 `assistant_operations(operation_type='delete_todo')`。

撤销时重新插入同 ID 待办、恢复 FTS 和关系，并触发日历重新创建或更新。

### 事件

事件删除采用可撤销关闭态：更新 `assistant_events.status='closed'`、清空置顶并增加 revision。所有首页、搜索、候选与详情入口只读取 active 事件，因此用户侧立即消失；事件进展和来源关系保留在后台，供撤销和审计。

若 `linked_todo_policy='delete'`，本地在提交时重新读取该事件全部有效关联待办并逐条校验 revision，然后与事件关闭在同一个独占事务提交。操作快照包含事件、待办和关系；任一对象冲突则整轮回滚，不出现事件已删但待办只删一部分。

撤销恢复事件 active 状态、置顶、待办、关系、FTS 与日历同步。

## 架构变化

- `action-types / protocol / prompt`：增加两类删除候选和事件关联待办策略。
- `action-schema`：重建带新 operation type 的操作表，复制并校验全部旧操作记录。
- `action-validator`：校验候选 ID、revision、明确删除意图和关联待办策略。
- `action-store`：在现有独占事务中执行删除、快照和回执。
- `action-undo`：支持对象当前不存在时的删除操作校验与按快照恢复。
- `event-store / retrieval`：closed 事件不进入首页、搜索、详情或模型候选。
- `db / calendar sync`：复用现有待办删除触发器，并增加从快照恢复待办的事务内方法。
- 不新增网络接口，不增加模型调用次数；事件确认使用正常下一轮对话。

## 失败与边界

- 候选不存在、版本变化或删除集合变化：不提交任何对象，回复说明内容刚有变化，请重试。
- 多个同名候选：追问，不删除。
- 事件有关联待办但去留未明确：追问，不删除。
- 日历没有权限或暂时失败：本地删除成功，补偿队列保留，设置页继续展示同步异常。
- 删除事件但保留待办：待办保留，原 event relation 不再参与 active 查询；撤销事件后关系自然恢复展示。
- 重复说同一个删除请求：已不存在或 closed 的对象不会再次成为候选，不产生第二次删除操作。
- 删除请求处理中被用户点击停止：事务不提交，任何对象都不删除。

## 方案取舍

采用“明确删除后直接执行 + 回执撤销；事件关联待办只在去留不明确时追问”。

- 不采用所有删除都弹确认：对明确待办删除造成重复打断。
- 不采用删除事件默认级联待办：可能误删仍需执行的行动。
- 不采用删除事件默认保留待办：违背用户可能希望整体清理的意图。
- 不立即物理清空事件历史：会使撤销、来源审计和误删恢复失效；先进入 closed 状态更符合现有可撤销操作模型。

## 验收标准

1. 键盘和语音输入均能删除唯一匹配的待办；首页与事件详情同步消失。
2. 删除有日历映射的待办后对应苹果日程进入删除同步；撤销后重新创建或更新。
3. 删除无关联待办的事件直接成功并从首页、搜索、详情入口和候选中消失。
4. 删除有关联待办的事件且未说明去留时，只出现一次追问，不提交操作。
5. 回答“保留”只删除事件；回答“一起删除”原子删除事件及全部关联待办。
6. 首轮已经明确待办去留时不重复询问。
7. 删除回执可以撤销；事件、待办、关系、FTS 和日历状态全部恢复。
8. 多候选、版本冲突、模型非法 ID、停止请求均不产生部分删除。
9. 原始对话消息始终保留，删除对象不会删除或改写聊天历史。
10. operation table 迁移保留全部旧操作记录，`npm run ci` 与真机验收通过。
