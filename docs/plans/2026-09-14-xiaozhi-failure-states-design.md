# “小知”异常状态设计

状态：用户已确认，已实施并通过自动检查；待设备异常注入验收

## 目标

把当前共用的页面错误拆成三类：首次加载失败、加载更早记录失败、AI 回复失败。每类错误只影响它实际破坏的能力，完整对话和已经保存的用户原话始终优先保留。

## 设计原则

1. 页面打不开才使用整页错误；局部动作失败只在局部提示。
2. 数据状态与模型状态分离：读取对话不调用模型，模型失败不伪装成页面加载失败。
3. 错误提示必须紧挨可恢复动作，不能同时在顶部和消息下重复出现。
4. 用户原话先保存；任何模型错误都不能删除、复制或改写原话。
5. 同一条连续对话同一时刻只允许一个 AI 回复请求，避免回复乱序。

## 方向一：首次加载失败

### 触发条件

用户进入“小知”后，首次读取本地消息失败，而且页面中没有可继续展示的历史消息。理解引擎设置读取失败不算对话加载失败，不能因此隐藏已经读到的消息。

### 页面

- 保留“小知 / 连续对话 · 自动保存”标题和底部三个 Tab，用户知道自己仍在正确位置。
- 中间只显示：`对话暂时无法加载`、`你的记录仍保存在本机，请重新尝试。`、主按钮 `重新加载`。
- 不显示首次使用空态、示例问题或“去配置”，避免把读取失败误认为没有历史。
- 输入框保留原位置但禁用，避免布局跳动，也避免用户在数据库不可用时误以为消息能被保存。

### 恢复流程

`点击重新加载 → 重新读取消息 → 成功则进入空态或历史态 → 失败则留在当前页`

重新加载只读本地数据库，不调用模型、不写消息。按钮执行期间显示小型加载状态并防止重复点击。

### 边界

- 如果消息读取成功、设置读取失败：继续显示对话；暂不显示“未配置引擎”判断，真正发送时再给准确反馈。
- 页面曾经成功加载过，随后刷新失败：保留已有消息，不退回整页错误。
- App 根数据库初始化失败仍由现有全局错误页处理；本页错误只处理“小知”消息读取失败。

## 方向二：加载更早记录失败

### 触发条件

用户已经看到当前对话，向上滚动加载更早一页消息时失败。

### 页面

- 已有消息、当前位置和输入框保持不变。
- 列表顶部的加载转圈替换为一行：`更早记录暂时加载不了 · 重试`。
- 不显示顶部全局错误条，不滚回底部，不清空当前消息。
- 输入框继续可用，因为当前消息已经成功读取，新增消息仍可按正常落库流程处理。

### 恢复流程

`点击重试 → 使用同一个分页游标读取 → 成功后去重并前插 → 保持用户当前阅读位置`

第一次失败后停止自动触发，只有用户点击“重试”或离开后重新进入才再次请求，避免滚动停在顶部时形成无限重试。

### 边界

- 重试返回重复边界消息：按消息 ID 去重。
- 重试成功但没有更早记录：移除提示并标记到底。
- 用户在失败提示存在时发送新消息：顶部提示保留，新消息正常显示在底部。
- 分页期间普通刷新发生：合并而不是覆盖，不改变当前游标。

## 方向三：AI 回复失败

### 触发条件

用户消息已经保存，但模型调用因未配置、网络、超时、服务错误或返回格式错误而失败。

### 页面

- 用户气泡保持原样；气泡下显示 `小知暂时没回复 · 重试`。
- 不再同时显示页面顶部错误条，避免同一错误出现两次。
- 点击“重试”后原消息不复制，状态变为 `小知正在想…`；成功后只增加一条助手回复。
- 未配置理解引擎时，顶部显示 `去配置`，消息下只写 `尚未回复`，不提供无效的立即重试。

### 并发与顺序

- 同一连续对话只允许一个回复请求；存在 `sending` 消息时输入框禁用。
- 请求失败后输入框恢复。用户可以先重试，也可以直接发送新的表达。
- 一旦用户发送了更新的消息，旧失败消息保留 `这条未回复`，但不再提供重试，防止旧回复在当前对话末尾乱序出现。
- App 进程仍存活、只是离开页面时，后台请求继续；重新进入显示 `小知正在想…`。
- App 被完全关闭时，进程内请求不可能继续。下次冷启动将数据库中遗留的 `pending` 请求改为可重试失败态，不能永久显示“正在想”。

### 错误文案

- 网络或超时：`小知暂时没回复 · 重试`
- 服务或格式异常：`回复出了点问题 · 重试`
- 未配置：`尚未回复`，同时使用顶部 `去配置`
- 被冷启动中断：`上次回复被中断 · 重试`

内部错误码保存在请求表中用于恢复和排查，但不直接展示给用户。

## 状态与数据流调整

页面不再使用一个 `pageError` 表达所有问题，而是分开维护：

- `initialLoad: loading | ready | error`
- `olderPage: idle | loading | error | exhausted`
- 每条用户消息自身的 `sending | saved | failed` 状态和后台错误码

数据流：

`首次读取失败 → initialLoad.error → 整页重试`

`向上分页失败 → olderPage.error → 顶部局部重试`

`模型失败 → message.failed → 消息下局部重试`

冷启动时增加一次本地恢复：把没有对应运行中任务的 `pending` 请求标记为 `interrupted`，不调用模型。

## 实施范围

- 调整 `app/(tabs)/assistant.tsx`，拆分首次加载、分页和回复错误状态。
- 调整 `AssistantMessageBubble`，按错误类型和是否仍可重试显示文案。
- 使用现有 `AssistantComposer.disabled`，在首次加载失败或有请求处理中禁用输入。
- 新增冷启动 pending 请求恢复仓储函数，并在数据库启动后执行。
- 扩展 UI、数据库和编排测试；所有测试继续由 `npm test` 聚合。

## 验收标准

1. 首次读取失败时看不到误导性的空态，输入不可发送，点击重新加载可恢复。
2. 加载更早记录失败时当前对话和滚动位置不变；未经用户点击不会循环重试。
3. AI 回复失败只在对应消息下出现一次提示，原话重启后仍存在。
4. 重试同一请求只产生一条用户消息和一条助手回复。
5. 存在回复中请求时不能再并发发送；成功或失败后输入恢复。
6. App 被完全关闭再打开后，不会有消息永久停在“正在想”。
7. 设置读取失败不阻塞已保存对话展示。
8. `npm run ci` 通过，并在 iOS 模拟器验证三种异常及恢复流程。
