# 标题与正文日期一致性设计

日期：2026-09-07  
状态：用户已确认，待实现与真机验收

## 目标

用户修改原声标题、正文或二者时，系统识别日期变化但不静默改动待办日期。待办排序、通知和晨晚提醒以 `dueAt` 为唯一生效日期；标题、正文只是可编辑文字。

## 交互稿

### 单一候选日期

```text
┌──────────────────────────────┐
│ 调整待办日期？               │
│                              │
│ 检测到日期从 9月10日         │
│ 变为 9月12日。               │
│                              │
│ [统一为9月12日]              │
│ [继续编辑]                   │
└──────────────────────────────┘
```

### 标题与正文冲突

```text
┌──────────────────────────────┐
│ 日期不一致                   │
│                              │
│ 标题：9月10日                │
│ 正文：9月12日                │
│                              │
│ [统一为标题日期：9月10日]    │
│ [统一为正文日期：9月12日]    │
│ [继续编辑]                   │
└──────────────────────────────┘
```

### 日期被全部删除

```text
┌──────────────────────────────┐
│ 未检测到日期                 │
│                              │
│ 是否清除原待办日期9月10日？  │
│                              │
│ [清除待办日期]               │
│ [保留9月10日]                │
│ [继续编辑]                   │
└──────────────────────────────┘
```

## 决策规则

1. 无修改：退出编辑，不写库。
2. 标题或正文只有一个明确候选日期：与原 `dueAt` 相同则直接保存；不同或原来无日期则询问一次，确认即代表统一全部日期。
3. 标题、正文日期相同：作为一个候选日期，只询问一次。
4. 标题、正文日期不同：必须由用户选择；选择后在明确授权下同步另一处日期文字。
5. 原文字包含日期、新标题和正文都不再包含日期：询问清除或保留 `dueAt`。
6. 同一字段出现多个不同日期：不猜测，提示用户继续编辑并保留一个待办日期。
7. 只改措辞、日期没有变化：保存文字，保留 `dueAt`。
8. 修改正文日期时同步标题中的待办日期；正文没有日期时不凭空添加。主题与完成状态始终保持不变。
9. 不提供“只保存文字但保留旧日期”的出口，避免主动制造不一致。
10. 相对日期保存为具体日期；有 `dueAt` 的记录标题必须包含具体日期。

## 数据流

```text
编辑标题/正文
  → 本地识别两处日期证据
  → 直接保存 / 日期确认 / 冲突确认 / 多日期拦截
  → applyCorrection 一次事务保存文字与明确的 dueAt
  → 同步 FTS 与通知补偿队列
  → 提交后重排到点通知及晨晚通知
```

## 边界与验收

- 覆盖只改标题、只改正文、同时修改，分别组合无日期、同日期、新日期、删除日期和冲突日期。
- 相对日期以点击完成时为基准，并在确认文案中显示具体日期。
- 多个不同日期不自动选择；无法识别时不改变 `dueAt`。
- 保存失败整体回滚，不出现正文已变、搜索或通知仍是旧内容的部分状态。
- 已完成记录仍保持完成；聚合主题不变；没有内容变化时 `updatedAt` 不变。
