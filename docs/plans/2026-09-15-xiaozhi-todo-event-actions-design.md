# 小知待办与事件操作设计

状态：已实施，等待 Dev 真机验收

## 1. 目标

让小知从“保存连续对话并回复”升级为能够可靠办理两类对象：

- 待办负责明确的下一步行动，包括创建、补充或修改日期、修改内容和完成。
- 事件负责需要持续跟踪的主线，包括创建、稳定标题、更新当前状态、追加关键进展、改名、置顶，以及关联待办。

同一轮可以同时改变待办和事件，但用户只看到一条自然回复和一张合并的“已处理”回执。普通讨论不为了显得聪明而强制创建对象。

## 2. 非目标

- 本阶段不实现长期记忆、教练提醒、统一搜索或每日复盘。
- 不删除首页备忘录、原声、长期待办数据或旧 `entries` 数据；首页不再单独展示长期待办模块。
- 不自动删除、归档或关闭事件。
- 不把每条消息、每个待办或每个主题都自动升级成事件。
- 不增加第二次模型调用来校验或改写同一轮结果。

## 3. 产品规则

### 3.1 待办与事件的分界

判断标准不是事情持续多久，而是它是否存在会继续变化、值得维护的主线状态。

- 一次性行动完成后即结束，只创建待办。
- 用户明确表达后续、逐步、长期、持续跟进、多阶段或多步骤时，可以创建事件。
- 当前消息是已有事件的新进展时，更新已有事件。
- 暂时证据不足时只保存消息或待办；后续出现第二次有意义的更新时再升级为事件，并回溯关联早期消息和待办。

新事件采用保守准入。系统自动创建的依据至少满足一项：

1. 用户明确要求持续记录、关注或跟进。
2. 当前表达包含清晰的持续性或阶段性信号。
3. 最近上下文中已经出现至少两条高度相关、且包含状态变化的表达。

### 3.2 事件内部结构

- `title`：稳定的主线名称，通常不随每次更新变化。
- `currentState`：当前状态摘要，允许被最新有效信息覆盖更新。
- `event_updates`：有意义的关键进展，只追加；普通追问、寒暄、重复表达和重复总结不进入。
- 关联待办：独立完成，但通过对象关系归属到事件。
- 来源消息：后台保留，用于追溯、纠正和重建，不直接铺满详情页。

标题仅在用户明确改名、纠正，或原名明显不准确时更新。旧标题保留为别名，事件 ID 和历史关系不改变。

### 3.3 同一事件识别

匹配顺序：

1. 从事件详情进入小知时携带的事件 ID。
2. 当前对话已绑定的事件主线。
3. 对事件标题、别名、当前状态和关联待办的本地检索结果。
4. 单一高置信候选可以自动更新。
5. 多个相近候选不能静默合并；小知只追问一个必要问题。
6. 没有候选且达到新事件门槛时创建新事件。

模型只能选择本轮上下文明确提供的候选 ID，不能生成任意事件或待办 ID。

## 4. 页面与交互

### 4.1 小知

- 助手回复保持现有气泡形态。
- 只有实际落库成功的操作才在回复下显示一张合并回执。
- 回执逐项显示“建立待办、完成待办、建立事件、更新事件、追加进展”等实际结果。
- 点击待办或事件回执行进入对应详情。
- 首版提供“撤销本轮”；若对象在本轮之后已经变化，停止自动撤销并提示用户通过小知纠正。
- 模型自然回复不得自行声称“已经保存”；成功事实以本地回执为准。

### 4.2 首页

- 现有本周待办继续使用 `entries(kind='task')`，因此小知创建的有日期待办自动进入本周。
- 新增事件区，卡片只显示稳定标题、当前状态和更新时间。
- 旧聚合主题迁移为事件后，不再在聚合卡区域重复展示；旧原声和未聚合记录暂时保留，等待后续首页整体重构。
- 本次不加入教练提醒。

### 4.3 事件详情

详情依次展示：事件标题、更新时间、置顶 / 更多、当前状态、关联待办、关键进展，以及底部“和小知聊这件事”。

- 关联待办可以直接完成，并同步到首页。
- “和小知聊这件事”进入同一连续对话，携带事件 ID，不新建会话。
- 改名通过更多操作完成；标题修改不改变事件 ID。
- 事件不存在或读取失败时显示局部错误和返回入口，不影响其他页面。

## 5. 高层架构

```text
用户消息先落库
  → 选择最近对话、相关事件和未完成待办
  → 一次模型调用返回自然回复、分段和候选操作
  → 本地校验事件准入、候选 ID、日期、重复与权限
  → 单个 SQLite 独占事务保存：回复 + 对象 + 关系 + 操作日志
  → UI 根据已提交操作生成合并回执
  → 首页与详情从同一事实表读取
```

模型负责语义建议，本地负责最终裁决。完整消息、待办、事件和关键进展是事实来源；事件检索投影、回执展示和上下文片段均可重建。

## 6. 数据模型

### 6.1 继续复用的事实

待办继续使用现有 `entries` 表中 `kind='task'` 的记录，避免首页、日历、通知、详情、备份同时维护第二份事实。

### 6.2 新增表

- `assistant_events`：`id`、`title`、`current_state`、`status`、`pinned_at`、`revision`、创建和更新时间。
- `assistant_event_aliases`：事件旧标题及别名，用于改名后的检索。
- `assistant_event_updates`：事件 ID、进展内容、发生时间、来源消息、撤销时间。
- `assistant_object_relations`：消息、事件、待办之间的 `source / belongs_to / follows / related` 关系。
- `assistant_operations`：请求 ID、稳定操作键、操作类型、对象类型和 ID、操作前后快照、回执摘要、状态和撤销时间。

回执不单独保存一份不可追溯文案，而是从已经提交的 `assistant_operations` 读取。操作键在请求内唯一，重试同一请求不能重复创建对象或进展。

## 7. 模型操作协议

现有 `{ reply, segment }` 扩展为 `{ reply, segment, operations }`。首版支持：

- `create_todo`
- `update_todo`
- `complete_todo`
- `create_event`
- `update_event`
- `append_event_update`
- `rename_event`
- `pin_event`
- `link_todo_event`

创建事件时使用本轮局部引用，例如 `event_ref: "event_1"`；同轮创建的待办可引用该局部引用。更新既有对象必须使用候选 ID。模型提供日期原文片段，本地以用户消息时间为基准调用现有中文时间解析器，模型不能直接写时间戳。

解析器限制操作数量和字段长度，拒绝未知类型、重复键、任意 ID、非法引用和空内容。

## 8. 本地校验与事务

- 新事件必须通过准入规则；未通过的创建建议被拒绝。
- 更新事件和待办只能指向本轮候选对象或显式启动上下文。
- 事件状态和进展与最新内容没有实质变化时跳过。
- 有日期行动写入现有待办并同步现有日历提醒队列；无日期行动作为隐藏待办保存。
- 每轮最多执行 6 个操作，防止异常输出批量写数据。
- 有效操作和助手回复在一个独占事务中提交；事务失败不保存回复和回执，用户消息继续保留为失败态。
- 解析成功但部分候选操作无效时，只执行有效操作；自然回复被约束为不声明执行结果，回执只列实际结果。

撤销采用补偿事务并校验对象版本：本轮后没有变化才自动还原；出现后续修改时拒绝破坏性回滚。

## 9. 旧主题迁移

每个非空旧 `topic` 幂等迁移为一个事件：

- 标题使用原主题名。
- 当前状态使用该主题最近一条记录的摘要。
- 创建一条初始事件进展，来源指向最近记录。
- 该主题下全部旧记录与事件建立来源关系，但不全部显示为关键进展。
- 原 `entries.topic` 和 `topic_preferences` 保留，作为回滚来源。
- 迁移按稳定键去重，重复启动不会产生重复事件或进展。

## 10. 失败模式与恢复

| 失败 | 用户结果 | 恢复 |
|---|---|---|
| 模型或网络失败 | 原话保留，无对象、无回执 | 消息下重试 |
| 操作协议非法 | 原话保留，标记格式失败 | 同请求重试 |
| 事件候选歧义 | 不更新事件 | 小知追问一个澄清问题 |
| SQLite 事务失败 | 回复与全部操作回滚 | 同请求幂等重试 |
| 首页事件读取失败 | 本周待办继续显示 | 事件区局部重试 |
| 事件已被改名 | 通过别名仍可匹配 | 使用稳定事件 ID |
| 撤销时对象已有后续变化 | 不自动覆盖新状态 | 引导用户通过小知纠正 |

## 11. 非功能要求

- 每条消息最多一次主模型调用。
- 事件和待办候选各最多 5 个，输入预算仍受现有上限控制。
- 所有写入本地 SQLite；API Key 和完整操作快照不进入日志。
- 请求与操作幂等，App 重启后可恢复失败状态。
- 旧数据库只新增表和迁移标记，不删除或重写旧事实。
- 新页面保持 44×44 最小点击目标，支持动态字体、加载、空态和错误态。

## 12. 架构决策

### ADR-04：待办继续使用 `entries`

决定：本阶段不新建第二份 `todos` 事实表。

原因：现有首页、日历、通知、编辑和备份全部依赖 `entries`。直接复用可以形成端到端闭环，并避免双写一致性。

代价：事件对象使用新模型，待办仍带有旧通用条目字段；以后如需拆表，必须通过兼容视图或版本化迁移完成。

### ADR-05：事件使用稳定 ID 和双层内容

决定：标题与当前状态可更新，关键进展只追加，所有关系绑定稳定事件 ID。

原因：既满足首页快速阅读，也保留过程历史；改名不会切断关联。

### ADR-06：模型建议、本地裁决

决定：模型不能直接写库，也不能决定成功回执。

原因：日期、事件准入、对象 ID、幂等和撤销必须确定、可测试、可追溯。

## 13. 验收标准

1. 一次性有日期行动只创建待办并进入本周，不创建事件。
2. 无日期行动保存为隐藏待办并最多追问一次；补充日期后更新同一待办。
3. 持续主线可以创建事件，标题稳定、当前状态更新、关键进展追加。
4. 已有事件的新消息能更新正确事件；多个相似候选不会被静默合并。
5. 同一轮可以更新事件、追加进展并创建关联待办，只显示一张合并回执。
6. 重试同一请求不产生重复待办、事件、进展或关系。
7. 模型或事务失败不显示虚假成功，不丢用户原话。
8. 首页显示本周待办和事件卡；事件详情正确展示四层结构。
9. 事件改名后历史关系和检索仍有效；置顶排序正确。
10. 本轮之后对象有新变化时，撤销不会覆盖新状态。
11. 旧聚合主题幂等迁移为事件，旧数据保持可回查和可回滚。
12. `npm run ci` 与 GitHub `CI / validate` 通过；Dev 真机完成创建、更新、重试、撤销和重启验收。
