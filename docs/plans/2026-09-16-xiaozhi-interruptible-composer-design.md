# 小知执行中可输入与可中止设计

状态：已实施，等待 Dev 端验收

视觉稿：[执行中输入框状态](../../design/xiaozhi-interruptible-composer-v18-portrait.svg)

## 目标与方案选择

目标是把“小知处理中”从一个锁死状态改为可控状态：用户可以继续组织下一句话，也能主动停止当前模型请求。它不允许两个模型请求并行，避免上下文顺序、事件更新和待办落库发生竞争。

比较三种做法：

1. **真正中止请求并原子收尾（推荐）**：输入框保持可编辑，右侧发送按钮变成停止方块；点击后通过 `AbortController` 终止流式请求，保留草稿和已显示的部分回复，但不提交任何待办、事件、记忆操作。
2. 只在 UI 上隐藏运行状态：实现简单，但模型仍消耗 token，完成后还可能偷偷落库，不符合“杀死”的含义。
3. 允许执行中继续发送、形成并行请求：速度最快，但两轮会共享过时上下文并竞争写入，不适合当前强调一致性的助手。

采用方案 1。

## 页面状态

### 空闲

输入框可输入、可语音；有文字时右侧为橙色发送箭头。

### 小知执行中

- 输入框不置灰，可继续输入和编辑下一条草稿。
- 右侧控制变为橙色停止按钮（白色方块），点击用于停止本轮。
- 当前轮未结束前不能发送第二条；麦克风暂不可用，避免录音与模型运行同时争夺输入状态。
- 上方仍显示流式回复和“小知正在处理”。
- 如果模型自然完成，停止按钮自动恢复为发送按钮，用户已输入的草稿原样保留。

### 点击停止

- 立即中止模型网络请求，不再进行自动重试。
- 已经显示的部分回复保留，并显示弱提示“已停止 · 未执行任何操作”。
- 如果尚未产生任何回复，只在该用户消息下显示“已停止”。
- 输入框中的草稿不清空，右侧恢复为发送按钮，可以直接开启下一轮。

## 执行链路与原子性

当前 Provider 已支持 `AbortSignal`，本轮把控制器提升到助手任务层，并按 `requestId` 管理正在运行的任务：

`用户发送 → 用户消息先落库 → 后台模型任务启动 → 输入框立刻恢复编辑 → 流式回复 → 自然完成或用户停止`

停止链路：

`点击停止 → AbortController.abort → Provider 停止读取流 → 事务写入 cancelled 收尾 → 清除运行态 → 保留草稿`

数据上继续复用现有 `failed + error_code` 表达请求终止，避免新增数据库 CHECK 状态和高风险迁移；产品层把 `cancelled` 单独解释为“已停止”，不展示“重试”。若已有部分回复，则只保存回复文字与停止标记；事件、待办、长期记忆、关系和回执均不写入。

提交操作的事务会先确认请求仍是 `pending`。若停止先到，提交整体拒绝；若完整提交已经先完成，停止不会回滚已经完成的结果，页面直接显示最终回复。这解决了“停止和落库同时发生”的竞态。

## 边界情况

- 用户在运行中输入草稿后切换 Tab：草稿沿用组件当前生命周期；返回页面时若组件未卸载则保留，模型任务继续运行。
- 连续点击停止：只处理第一次，后续点击无副作用。
- 停止发生在 Provider 自动重试前：取消信号阻止第二次请求。
- 网络恰好返回完成：以数据库事务先获得提交权的一方为准，不出现“操作落库但页面显示已停止”。
- 停止后部分回复不得带操作回执，也不能触发首页待办、事件或长期记忆变化。
- 语音输入仍只在没有模型任务运行时开放；文字输入始终可用。

## 验收标准

1. 小知执行中输入框保持白色、可输入、可编辑，不再清空后锁死。
2. 执行中右侧显示停止方块；点击后真实终止网络请求，且不会自动重试。
3. 执行中不能发送第二条，停止或自然完成后发送按钮自动恢复。
4. 执行期间输入的草稿在自然完成、停止或失败后都不丢失。
5. 停止时保留已显示的部分回复并标注“已停止”；没有部分回复时用户消息下显示“已停止”。
6. 停止的请求不生成或更新待办、事件、长期记忆、关系与回执。
7. 完成与停止竞态下只出现一个最终状态，不存在半落库。
8. Provider 取消、任务单飞、停止收尾、草稿状态和 UI 按钮状态均有自动化测试并纳入 `npm test`；完整 `npm run ci` 通过后在 Dev 端验收。
