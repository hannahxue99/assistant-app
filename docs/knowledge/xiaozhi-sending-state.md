# 小知发送状态：单一反馈与草稿安全

## 背景与结论

小知原先在用户消息下和输入框内同时显示转圈，而且输入内容要等模型完整返回后才清空。真机上看起来像同一条消息正在发送两次，也让用户不确定能否继续操作。

最终交互是：点击发送后，用户原话先落库并立即进入消息列表；输入框立即清空、失焦、置灰，处理进度只在用户消息下显示一次。回复成功、失败或超时后恢复输入。模型失败不恢复草稿，因为用户原话已经保存；只有本地落库失败才恢复原文。

## 根因与关键取舍

- 根因：`AssistantComposer` 把清空动作放在 `await onSend()` 之后，并在本地 `sending` 状态下额外渲染一个 `ActivityIndicator`；消息气泡又根据持久化的 `sending` 状态渲染第二个反馈。
- 进度属于“这条消息的回复状态”，应靠近消息展示；输入框只表达当前是否可输入，不承担第二套进度反馈。
- 草稿是否恢复必须以“用户原话是否成功落库”为边界，不能简单按模型调用成功或失败判断，否则模型失败时可能制造重复发送。

## 可复用实现模式

1. 点击发送时先快照 `content` 和输入来源，再立即清空本地草稿、禁用输入并收起键盘。
2. `saveUserTurn` 成功后，直接把返回的用户消息合并进页面状态，再启动模型调用；不要为了显示消息先依赖一次额外全量刷新。
3. 页面持久状态通过 `hasPendingAssistantReply(messages)` 表达，输入组件本地状态负责填补落库前的短暂间隙，两者共同保证单飞。
4. 输入组件不渲染加载指示器，只显示禁用背景和 `小知回复后可继续输入`。
5. `onSend` 只有在用户消息没有保存成功时向输入组件抛错；消息已保存后的模型错误由对应消息的失败状态与重试动作承载。

## 易错点

- 先保存、再刷新、再调用模型时，如果刷新失败会把已经保存的消息误判为“未发送”，恢复草稿后容易重复创建；应直接使用 `saveUserTurn` 的返回值乐观合并。
- 只依赖父组件的持久化状态会在落库前留下可重复点击窗口；只依赖输入组件本地状态又无法覆盖离开再进入页面后的在途请求，两层状态都需要。
- 初次加载失败与模型处理中都会禁用输入，但只有模型处理中使用“回复后可继续输入”文案。

## 验证方式

- 自动：`npm run ci`，包含 TypeScript、消息状态、数据库、模型编排和多轮上下文测试。
- 真机：发送后确认原话立即进入列表，输入框清空置灰且没有第二个转圈；成功、失败或超时后输入恢复。
- 用户于 2026-09-15 在 Dev 版确认该交互正常。
