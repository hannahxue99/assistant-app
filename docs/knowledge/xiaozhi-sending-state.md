# 小知发送状态：可中止运行与草稿安全

## 背景与结论

小知早期在用户消息下和输入框内同时显示转圈，而且输入内容要等模型完整返回后才清空。随后采用过“发送后输入框置灰”的过渡方案，但它阻止用户在等待时准备下一段内容，也不符合主流对话产品的中止心智。

最终交互是：点击发送后，用户原话先落库并立即进入消息列表，输入框立即清空并保持可编辑；右侧发送按钮在运行期间变为停止按钮。用户可以先输入下一段草稿，但前一轮结束或被停止前不能把它作为新请求发送。模型失败不恢复上一条原文，因为用户原话已经保存；只有本地落库失败才恢复原文。

## 根因与关键取舍

- 根因：`AssistantComposer` 把清空动作放在 `await onSend()` 之后，并在本地 `sending` 状态下额外渲染一个 `ActivityIndicator`；消息气泡又根据持久化的 `sending` 状态渲染第二个反馈。
- 进度属于“这条消息的回复状态”，应靠近消息展示；输入框保留编辑能力，按钮只表达当前可发送还是可停止。
- 草稿是否恢复必须以“用户原话是否成功落库”为边界，不能简单按模型调用成功或失败判断，否则模型失败时可能制造重复发送。
- 停止是对当前网络请求的取消，不等于发送输入框里的新草稿；未完整返回的结构化操作不得落库。

## 可复用实现模式

1. 点击发送时先快照 `content` 和输入来源，再立即清空本地草稿；输入框继续接收下一段文字。
2. `saveUserTurn` 成功后，直接把返回的用户消息合并进页面状态，再启动模型调用；不要为了显示消息先依赖一次额外全量刷新。
3. 页面持久状态通过 `hasPendingAssistantReply(messages)` 表达，输入组件本地状态填补落库前的短暂间隙，两者共同保证同一时刻只有一个请求。
4. 运行中把发送按钮切换为停止按钮；停止时中止 fetch/流读取、清理临时回复，并把本轮标为取消，不执行模型尚未完成的操作。
5. `onSend` 只有在用户消息没有保存成功时向输入组件抛错；消息已保存后的模型错误由对应消息的失败状态与重试动作承载。

## 易错点

- 先保存、再刷新、再调用模型时，如果刷新失败会把已经保存的消息误判为“未发送”，恢复草稿后容易重复创建；应直接使用 `saveUserTurn` 的返回值乐观合并。
- 只依赖父组件的持久化状态会在落库前留下重复请求窗口；只依赖输入组件本地状态又无法覆盖离开再进入页面后的在途请求，两层状态都需要。
- 用户切换到首页不会自动终止请求；小知页返回时应恢复原滚动位置，而不是强制滚到最底部。
- 取消后必须保证数据库中没有半个事件、待办或记忆变更；流式文字和业务提交使用不同边界。

## 验证方式

- 自动：`npm run ci`，包含 TypeScript、消息状态、数据库、模型编排和多轮上下文测试。
- 真机：发送后确认原话立即进入列表；运行中可继续输入，按钮显示停止；停止后草稿保留，当前请求结束且无业务操作落库。
- 用户先于 2026-09-15 验收过置灰版，随后明确要求并确认实现可编辑、可停止的最终方案。
