# V1 产品口径：完整愿景与实现进度分离

## 产品决策

原“秘书 + 导师 V0.3”完整方案正式升级命名为 **V1 产品愿景**。V1 的完整定义是：一个长期懂你的私人 AI，能够听懂、执行、记住、延续，并在出现新价值时主动引导。

当前手机版本只完成了其中的主要基础能力。产品文档必须同时标注：

- **目标能力**：V1 完整闭环应该包含什么。
- **实现状态**：当前版本中哪些已实现、部分实现或未实现。

版本号、产品愿景和发布状态是三个不同概念：`app.json` / `package.json` 的 `1.0.0` 是构建版本；V1 是产品范围；某项能力只有经过代码、自动检查和真机验收后才算已交付。

## 关键取舍

没有采用“已上线能力就是 V1”的窄口径。原因是每日复盘、教练提醒和统一搜索属于“秘书 + 导师”成立所需的核心闭环，移到 V1.1 会让 V1 只剩会聊天和记事的助手，弱化“长期理解并主动引导”的产品承诺。

代价是 V1 在一段时间内处于“部分实现”状态。因此 PRD 必须维护带日期的进度矩阵，发布知识文档必须记录具体交付；README 只表达稳定的产品愿景，不能同时充当发布说明。

## 容易踩的坑

1. **把版本号当完成状态**：代码已经是 `1.0.0`，但不代表所有 V1 验收项已经通过。
2. **把设计文档当上线清单**：历史设计写了教练提醒、每日复盘和统一搜索，当前代码尚未实现。
3. **只更新 README 标题**：旧 PRD、工作决策和知识索引会继续传播冲突口径。
4. **覆盖历史文档来源**：保留原文件名和决策编号便于追溯，只在正文增加 V1 映射和新的事实来源。
5. **把代码合并当手机发布**：Release 必须单独记录设备、系统、Bundle ID、安装与启动结果。

## 可复用维护模式

以后产品信息统一使用三层描述：

1. `README.md`：面向所有读者的产品宣言，只解释为什么存在、希望建立怎样的人机关系，以及“料理当下、看清方向”的长期愿景。
2. `PRD.md`：产品目标、原则、完整范围、验收标准和带日期的实现进度。
3. 发布知识文档：具体 PR、提交、CI、设备交付与回滚记录。

新能力完成后只更新状态，不重新发明版本定义。若产品范围发生变化，先改 PRD 和设计图，再进入代码实现。

## README 产品宣言（2026-10-05）

PR #36 将 README 从功能说明改为宏观产品宣言，并在用户验收中进一步确认：项目入口不应由当前版本已经实现什么来定义，而应首先讲清楚个人助手与人的长期关系。

最终叙事以“像秘书一样帮你料理当下，像导师一样帮你看清方向”为中心，形成五个稳定概念：

1. 同一个助手同时面对当下事务与长期方向，不把秘书和导师拆成模式。
2. 从自然对话开始，逐渐形成可纠正、会随经历变化的长期理解。
3. 主动的价值不在频繁提醒，而在信息真正产生新意义时让重要事情浮现。
4. 助手帮助人行动和思考，但不替人做决定，也不把猜测当事实。
5. 产品的目的不是接管生活，而是减少认知负担，把注意力还给重要的关系、选择和创造。

可复用的文档原则是：README 保持宏观、稳定、与具体实现解耦；页面、对象、配置和交付细节分别进入 PRD、CURRENT、专题知识与发布记录。竞品理念可以启发叙事角度，但不得在没有可靠来源时写入具体竞品结论或引用。

## 验证方法

- `rg -n "V0\.3" README.md PRD.md docs`：剩余 V0.3 只能出现在历史映射、文件名或原方案说明中。
- 对照 `app/(tabs)`、`src/assistant`、数据库表和自动测试核实进度矩阵，未找到运行时实现的能力不得标为完成。
- 运行 `npm run ci`，确认文档更新没有伴随错误的运行时代码或测试变更。
- 审查 Git diff，改动范围应只有 Markdown 与设计 SVG。
- PR #36 验证了核心 Markdown 相对链接、`npm run test:agent-tooling` 与完整 `npm run ci`；GitHub `CI / validate` 通过，用户于 2026-10-05 明确验收 README 产品宣言。
