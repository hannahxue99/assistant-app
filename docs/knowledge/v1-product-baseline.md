# V1 产品口径：完整愿景与实现进度分离

## 产品决策

原“秘书 + 导师 V0.3”完整方案正式升级命名为 **V1 产品愿景**。V1 的完整定义是：一个长期懂你的私人 AI，能够听懂、执行、记住、延续，并在出现新价值时主动引导。

当前手机版本只完成了其中的主要基础能力。产品文档必须同时标注：

- **目标能力**：V1 完整闭环应该包含什么。
- **实现状态**：当前版本中哪些已实现、部分实现或未实现。

版本号、产品愿景和发布状态是三个不同概念：`app.json` / `package.json` 的 `1.0.0` 是构建版本；V1 是产品范围；某项能力只有经过代码、自动检查和真机验收后才算已交付。

## 关键取舍

没有采用“已上线能力就是 V1”的窄口径。原因是每日复盘、教练提醒和统一搜索属于“秘书 + 导师”成立所需的核心闭环，移到 V1.1 会让 V1 只剩会聊天和记事的助手，弱化“长期理解并主动引导”的产品承诺。

代价是 V1 在一段时间内处于“部分实现”状态。因此 PRD 和 README 必须提供进度矩阵，不能把愿景文案直接当发布说明。

## 容易踩的坑

1. **把版本号当完成状态**：代码已经是 `1.0.0`，但不代表所有 V1 验收项已经通过。
2. **把设计文档当上线清单**：历史设计写了教练提醒、每日复盘和统一搜索，当前代码尚未实现。
3. **只更新 README 标题**：旧 PRD、工作决策和知识索引会继续传播冲突口径。
4. **覆盖历史文档来源**：保留原文件名和决策编号便于追溯，只在正文增加 V1 映射和新的事实来源。
5. **把代码合并当手机发布**：Release 必须单独记录设备、系统、Bundle ID、安装与启动结果。

## 可复用维护模式

以后每个 V1 能力统一使用三层描述：

1. `PRD.md`：产品目标、原则、完整范围和验收标准。
2. README 进度表：面向项目入口的“已实现 / 部分实现 / 未实现”。
3. 发布知识文档：具体 PR、提交、CI、真机与回滚记录。

新能力完成后只更新状态，不重新发明版本定义。若产品范围发生变化，先改 PRD 和设计图，再进入代码实现。

## 验证方法

- `rg -n "V0\.3" README.md PRD.md docs`：剩余 V0.3 只能出现在历史映射、文件名或原方案说明中。
- 对照 `app/(tabs)`、`src/assistant`、数据库表和自动测试核实进度矩阵，未找到运行时实现的能力不得标为完成。
- 运行 `npm run ci`，确认文档更新没有伴随错误的运行时代码或测试变更。
- 审查 Git diff，改动范围应只有 Markdown 与设计 SVG。
