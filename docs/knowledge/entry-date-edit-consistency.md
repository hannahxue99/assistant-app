# 原声编辑与待办日期强一致性

## 产品决策

- `dueAt` 是一条记录唯一生效的待办日期，决定待办排序、到点通知及晨晚提醒。
- 标题必须包含具体待办日期；正文可以没有日期，但正文中的待办日期必须与标题及 `dueAt` 相同。
- 修改标题、正文或二者时，一次编辑最多询问一次。用户选择最终日期即代表授权同步标题、正文、`dueAt` 和通知。
- 不提供“保存新文字但保留冲突旧日期”的入口。检测到多个不同日期时不猜测、不保存，要求用户继续编辑。
- 相对日期和 `M.D` / `M．D` 在确认后规范成 `M月D日`。正文没有日期时不凭空添加。
- 聚合主题和完成状态不随日期编辑改变。

## 根因与踩坑

旧编辑链路有两层隐式行为：数据库层在正文变化时自行重算日期并可能改写标题；页面层又只在部分冲突分支同步文字。结果是标题、正文、`dueAt` 可能分别保存不同日期。

首次修复仍漏掉两个问题：单一新日期确认只更新 `dueAt`，没有对称更新另一字段；日期解析器不认识用户常用的 `10.1`，把正文误判为“无日期”。因此仅测试 `10月1日` 不足以覆盖真实输入。

## 可复用实现模式

1. 保存前使用纯函数同时分析标题、正文和当前 `dueAt`，产出直接保存、统一确认、清除确认、冲突选择或多日期拦截五类决策。
2. 所有确认都在写库前完成；数据库层只应用明确 patch，不替交互层猜日期或改标题。
3. 用户选定日期后，统一规范标题和正文中的日期表达式，再通过独占事务保存记录、FTS 和通知补偿队列。
4. 提交成功后同步单条到点通知并重排晨晚通知；通知失败不回滚已保存内容，由补偿队列在后续启动恢复。
5. 日期解析新增格式时，必须同时覆盖：时间解析、日期证据提取、文字规范化和端到端编辑决策测试。

## 验证方法

- 专项矩阵：只改标题、只改正文、同时修改；分别覆盖无日期、同日期、新日期、删除日期、冲突日期和多个日期。
- 真实回归：正文 `10.1买菜`、标题从 `10月1日买菜` 改为 `10月2日买菜`，选择统一后标题和正文均为 `10月2日买菜`，`dueAt` 同步为 10 月 2 日。
- 自动检查：TypeScript、编辑日期决策、35 项时间解析、SQLite 编辑事务、通知隔离及全部既有业务测试通过；iOS Expo export 通过。
- 真机：用户在 iPhone 17 / Debug Development Build / Metro Reload 验收并于 2026-09-08确认通过；本次未读取到具体 iOS 版本。
