# 数据库启动与通知异常隔离

## 决策与根因

- SQLite 就绪是数据访问的前置条件。所有读写入口必须等待同一初始化 Promise，完成建表和迁移后才能发布实例。
- Fast Refresh 可能保留页面状态却重新执行模块；数据库运行时放在 globalThis 中复用，失败后允许重试。
- 单条提醒属于保存后的副作用。通知异常不得触发 LLM 降级，否则成功生成的主题可能被规则结果清空。
- 通知调用前写入补偿队列；失败时保留意图，启动时补偿。通知与补理解分别捕获异常。
- 真正的关键启动失败显示友好重试页；不要在失败后直接放行主页面。

## 验证与局限

- single-flight 测试覆盖并发共享、实例复用、失败重试。
- `node scripts/test-notification-isolation.cjs` 执行真实理解和通知模块，替换原生依赖模拟失败，验证新增、模型回填和完成时保存结果不被通知异常污染。
- 替身测试不代表真机通知送达验证。
- 待继续处理：删除通知补偿、按版本确认队列、防止并发编辑丢失补偿意图；日期与模型写入一致性另批处理。
- 以后修改数据库 schema 后需完整 Reload，避免开发运行时复用旧初始化结果。
